Render pipeline audit

reels-engine, 8 October 2026. Read-only: nothing was run, changed or tested. Every item below keeps the finished video looking exactly the same.

What was looked at: the five skills (video-pipeline and its five reference files, /content-talking-head, /content-vlog, /content-trial-reels, /content-tts) and every engine script that touches video: render.py, vlog.py, textreel.py, batch.py, grade.py, common.py, broll.py, review.py, takes.py, analyse.py, qc.py, plus the real filter scripts left in work/ from past renders and the properties of the actual source files.

What "won't alter the look" means here. Each suggestion is graded:

A bit-identical the frames going into the encoder are the same bytes. B identical to the eye differences at the level of a rounding error or encoder noise, same class as changes the engine has already accepted. C look into first real speed potential but it needs a measurement before anyone touches it. D previews only speeds up drafts and checks, never the final file.

Estimates are reasoned, not measured. The only measured number is the skill's own baseline: a 1:33 reel renders in about 1m30s wall time using 279 s of processor time (about three cores busy on a machine with ten).

Status: items 1 to 12 done

Done 8 October 2026. Checked by rendering the same plans before and after with a lossless encoder and comparing every frame (synthetic 8 and 10-bit, SDR and HLG, 30 and 60 fps, portrait and landscape sources). Speed was not measured on a Mac.

  • Bit-identical, as predicted: items 1 to 8 (one-pass talking head, text reels, review thumbnails, the 60 fps HDR vlog clip). Item 6 batches up to 24 thumbnails per ffmpeg run.
  • Item 9 (chunks) is bit-identical to a one-pass render, picture and sound, once two things were fixed. First, frame timing was not exact: each piece's sound was trimmed to the millisecond, which nudged later frame times by fractions of a millisecond. Whether a b-roll shot snapped onto a cut started on that cut's first frame (or let one talking-head frame flash) depended on that drift. Sound is now exactly as long as its frames, the joined picture counts in whole frames, and b-roll covers the frames nearest its edges. Against the old code that moves a fade or caption step by one frame now and then (73 dB average, 53 dB worst frame) and the sound by under 0.5 ms per cut. Second, ffmpeg picks the grade's pixel format from the whole graph (see item 13 below), so each chunk is held to the format the whole reel would use. tests/test_media.py checks chunks against one pass frame by frame. Reels of 30 s or more split into 2 chunks, 45 s or more into 3.
  • Item 10: parts are stream copies starting on the keyframe in the pause before each hook. Where that keyframe falls back inside the previous video's speech (long keyframe gaps), that part is re-encoded exactly as before, so a part never opens with the end of the previous video. Picture and sound line up as closely as the old re-encode did.
  • Item 11: 72 to 77 dB average against the old code on HDR (worst frame 53 to 65 dB).
  • Item 12: portrait clips at normal framing are bit-identical. Landscape clips and 1.15 tight framings now crop a window within about one source pixel of the old one (under 2 output pixels), the sub-pixel shift the report expected. On a fractal test pattern that reads as low PSNR (27 to 36 dB), because any shift does there.
  • Item 13 finding: with a slow zoom anywhere in the reel, ffmpeg grades in 8-bit planar RGB, because the zoom filter can't do more. Only reels with still shots alone grade 10-bit footage at 10-bit. So the "higher precision on a 10-bit source" note below only holds for reels without slow zooms. Nothing was changed for this; it's a look question.
  • Also new: a size-capped h.265 upload for TikTok Shop (--max-mb), see the video-pipeline skill.

Where the time goes

A finished talking-head reel is one ffmpeg command. For the 92.6 s DJI reel in work/ that command has 22 talking segments, 7 b-roll shots and 9 sound effects as separate inputs (38 inputs). Per frame, the work is roughly:

  • Decode runs on the Mac's media engine and is not the bottleneck. Every input is a 10-bit HEVC phone file (DJI 1728x3072 at 29.97 fps, or iPhone 4K at 60 fps, HDR on the iPhone clips). The decoded frames are copied back to normal memory for the filters.
  • Framing: still shots crop the exact window and scale once (already optimised). Slow zooms and every b-roll shot go through a 2160x3840 canvas and the zoompan filter, which rebuilds its scaler for every frame and only uses one core. This is the single most expensive thing in the chain.
  • Grade: one 3D colour table pass plus a light sharpen, both multi-core. Already optimised.
  • Text: two separate caption renderers run over every frame (graphics, then captions), one core each.
  • Encode: hardware h.264, effectively free.

The filter graph itself is scheduled on one thread. Filters that support slice threading (scale, colour table, sharpen, overlay, HDR conversion) fan out to other cores while they run; zoompan and the caption renderer do not. That is why a render uses about three cores on a ten-core machine and why items 5, 9 and 14 are the ones with real headroom.

A. Bit-identical changes

1. Drop to 30 fps before any picture work

Where: engine/commands/render.py frame_filter() lines 134 to 152 and build() line 563, broll_filter() lines 457 to 460; engine/commands/vlog.py video_chain() lines 311 to 315; engine/commands/textreel.py render_reel() lines 220 to 223.

NowThe chain per clip is: HDR conversion (4 colour passes in floating point, if the clip is HDR), then crop, scale, and only then fps=30. For a 60 fps iPhone clip every second frame goes through all of that and is then thrown away by the fps filter. 41 of the 85 clips in inputs/vlog/ are 4K, 60 fps and HDR; so is inputs/talking-head/old/IMG_4440.MOV. The b-roll library is 30 fps, so this costs nothing there.
ChangeMove fps=30 to the front of each chain, straight after the setpts reset (in vlog, after the speed setpts, since fps must see the retimed stamps). Everything else stays in the same order.
Why identicalThe fps filter chooses frames by timestamp only; it never looks at pixels. The frames that survive are exactly the same source frames, and each one then goes through exactly the same spatial filters as before. The b-roll chain and the textreel chain already have fps before zoompan, they just have scale and crop ahead of it.
GainOn 60 fps HDR sources: half the HDR conversion, half the scaling, half the memory traffic. On 30 fps sources: none. This is the biggest free win for vlog edits and trial reels, which draw on that library.

2. Trim to the exact frame count before the heavy filters

Where: engine/commands/render.py build() lines 559 to 565 and _render_windows() lines 710 to 712, broll_filter() lines 460 to 465; engine/commands/textreel.py lines 222 to 225.

NowEach segment is read with 0.3 s of slack (-t dur + 0.3), goes through crop/scale or the 2x canvas plus zoompan, and only then hits tpad (clone the last frame if short) and trim=end_frame=N. So 9 extra frames per segment are fully framed and zoomed and then dropped. B-roll reads 0.5 s of slack and keeps 4 spare frames, so about 11 frames per shot are wasted. Text reels read 0.4 s of slack.
ChangeOrder the chain as setpts, fps=30, tpad, trim=end_frame=N, then crop/scale/zoompan. The zoompan expression (on/N) does not change.
Why identicaltpad clones a frame and trim counts frames; neither cares what the pixels are. zoompan with d=1 produces one output per input, and each output depends only on its own input frame and the frame counter on, which runs 0 to N-1 either way. Today zoompan runs to N+8 and trim drops the tail; afterwards it stops at N. The first N frames are byte for byte the same.
One edge caseIf a source clip genuinely runs out (a segment that ends at the very end of the file), today the zoom freezes on the last rendered frame; after the change the cloned frame keeps zooming. Arguably nicer, but it is a difference, and it can only happen at the tail of a file. Not an issue for text reels, where the padding already sits before zoompan.
GainOn the sample reel: 22 x 9 = 198 extra frames out of 2778 through the framing stage, plus about 77 b-roll frames through the 2x zoompan path. Roughly 5 to 8% of frame work.

3. Run the pre-render scans concurrently, and cache the silence map

Where: engine/commands/render.py build() line 546, silence_map() line 533, scene_cuts() line 517; has_huesaturation() in engine/core/grade.py line 111, called at render.py 859 and vlog.py 353.

NowBefore anything renders, the engine runs the silence scan (audio decode of the whole file), then the scene-cut scan (a full video decode of the whole source at full resolution: 5,600 frames of 1728x3072 10-bit for the 187 s DJI clip), then spawns ffmpeg -filters to check a filter exists, then checks the colour table cache. All one after another. The scene scan is cached per file; the silence scan is not, so it reruns on every invocation, and a reel typically gets three or more (--cuts, --spot, final, re-renders after feedback).
ChangeCache the silence map the same way scene cuts are cached (by inode, size and mtime, in work/_scenes/ or a sibling). Start the scene scan and the silence scan as two threads and join them. Cache the has_huesaturation() answer keyed by the ffmpeg binary's path and mtime.
Why identicalSame commands, same numbers, just not waited for in sequence.
GainA few seconds per invocation; on the first run with a long 4K source the two scans overlap instead of adding up.

4. Scan b-roll for built-in cuts at index time

Where: engine/commands/render.py broll_windows() lines 436 to 445 calls scene_cuts() on every b-roll clip; engine/commands/broll.py cmd_index() line 45.

NowThe first time a b-roll clip is placed in a plan, the render build does a full-resolution decode of that whole clip to find scene changes. The library clips are 2160x3840 at 22 to 26 Mbps; the sample reel used 7 of them, about 2 minutes of 4K footage scanned while she waits for the render to start. It is cached after that, so it only bites once per clip, but it bites during a render.
Changebroll.py index already probes and previews each new or changed clip; add the scene scan there (and run several at once, item 5). The render then finds a warm cache.
Why identicalSame scan, same cache file, different moment.

5. Three jobs at a time inside the batch tools

Where: engine/commands/textreel.py cmd_render() line 258; engine/commands/vlog.py cmd_analyse() line 107; engine/commands/render.py _render_windows() line 695; engine/commands/batch.py cmd_cut() line 78.

NowThe skill says to render three videos at a time for sets, but the scripts themselves are strictly sequential: 30 trial reels one after another; 85 vlog clips measured one after another (each is a full 60 fps 4K decode plus 8 seeks for the frame sheet, which is why the skill says "run it in the background"); 20 to 25 cut-preview windows rendered one after another, each followed by its own flash scan; batch parts cut one after another.
ChangeA small worker pool (three workers, matching the skill's own rule for the four performance cores) in each of those loops. Outputs are collected in order so tables and the joined preview come out unchanged.
Why identicalEvery job is independent and deterministic; the same command produces the same file whether or not another ffmpeg is running next to it.
GainUp to about 2.5x wall-clock on those steps. For 30 trial reels or an 85-clip analyse that is minutes.

6. Review thumbnails in one ffmpeg call

Where: engine/commands/review.py thumb() lines 19 to 22.

NowOne ffmpeg process per line. The DJI reel has 41 lines, so 41 processes each open the 1.3 GB file, start a hardware decoder session, seek, decode one picture, and exit.
ChangeOne ffmpeg with 41 -ss inputs and 41 single-frame outputs (-map k:v -frames:v 1 each), the same way takes.py and the vlog contact sheet already batch their seeks.
Why identicalSame seek, same decode, same scale, same JPEG quality setting, so the same bytes.

7. Stop probing the same clip repeatedly in the vlog render

Where: engine/commands/vlog.py cmd_render() line 376; sdr_filter() in engine/core/common.py line 105.

NowInside the render loop every piece spawns ffprobe to ask whether its clip has audio. The HDR check probes again (that one is cached per path). A vlog plan has 40 to 50 pieces drawn from fewer clips, so the same file is probed several times.
ChangePut functools.lru_cache on probe() in common.py (paths do not change during one run), or read has_audio from clips.json, which already stores it.
Why identicalSame answer, fewer processes. Saves a few seconds per vlog render.

8. Burn graphics and captions in one pass

Where: engine/commands/render.py lines 885 to 886 (subtitles=graphics.ass, subtitles=captions.ass) and write_ass().

NowTwo caption renderers are set up and both touch every frame: graphics first, captions drawn on top.
ChangeWrite one .ass file containing both sets of events, with the Caption style on a layer above every graphics layer (for example layer 10; today captions are layer 0 and graphics 1 to 3). The CapCut matte export at lines 924 to 925 must keep its separate graphics file and is unaffected.
Why identicalThe caption renderer draws its glyph images onto the frame one by one, ordered by layer then by event. Two passes draw graphics then captions; one file with captions on the top layer draws them in exactly the same order, so every blended pixel is the same. Captions and graphics rarely overlap anyway (hook at the top, captions at 70% height).
GainSmall: one per-frame renderer call instead of two, one font load. Worth it because it is trivial.

B. Identical to the eye

These change bytes at the level of a rounding error or of how the encoder packs the same pictures. The engine already accepted this class of change once (still framings now crop then scale instead of going via the 2x canvas, documented as "identical framing").

9. Render a single reel in two or three parallel chunks

Where: engine/commands/render.py main() lines 880 to 889, one ffmpeg for the whole timeline. Helper that already exists: _shift_events() line 685.

NowOne process, one filter graph, one scheduling thread. The two single-threaded stages (zoompan and the caption renderer) cap throughput at roughly real time: a 92 s reel takes about 90 s and leaves most cores idle while the hardware encoder waits. For sets the skill already works around this with three renders at once; a single reel cannot.
ChangeSplit the segment list into two or three chunks at cut boundaries, choosing boundaries where no animated graphic straddles the join (hook fade, stat pop count-up, takeover scale-in; captions in build mode have no animation). Render each chunk's video only in parallel with the same filters and a time-shifted .ass (what _shift_events does for cut previews), join them with -c copy, render the audio once as today (the loudness normaliser needs the whole timeline, and audio is cheap), and mux.
Why class BThe pixels handed to the encoder are identical: every segment is self-contained (its own input, its own zoom expression), the grade is per frame, and shifted captions land on the same frames. What differs is the encoded bitstream: a keyframe is forced at each join and the rate control starts fresh per chunk. At 10 Mbps on talking-head footage that is not something a viewer can see, but it is not the same bytes.
GainPotentially 1.5x to 2.5x on every final render (unmeasured). This is the largest item on the list and also the most work.

10. Cut shop batches without re-encoding

Where: engine/commands/batch.py cmd_cut() lines 58 to 84.

NowEach shop part is re-encoded with the hardware HEVC encoder at quality 80 (the parts in work/ came out at 36 to 49 Mbps). That means decoding and encoding the whole 5-minute 4K batch before the real edit starts, and it puts one extra lossy generation between her camera and the finished reel. The parts also get +faststart, a second rewrite of each 170 MB file, for a feature only uploads need.
ChangeCopy the streams instead: -c copy -avoid_negative_ts make_zero. The cut snaps to the keyframe before each section start, so a part can begin a second or two early. That is harmless here because every part is transcribed and planned from scratch afterwards and the planner cuts dead air anyway. Drop +faststart on intermediates. A further option that avoids cutting entirely: hard-link the batch file once per part (the compilation workflow already does this) and restrict each plan to that section's words.
Why class BThe finished reel is then rendered from the original pixels rather than from a re-encode, so it moves one generation closer to the source. A tiny improvement, not a difference she could see, but strictly a change.
GainThe cut step becomes near-instant instead of minutes.

11. Crop before the HDR conversion on still framings

Where: engine/commands/render.py build() line 563: {sdr_filter} runs before frame_filter().

NowFor HDR sources the four-pass floating-point conversion runs on the full source frame, then the still-framing path crops a window out of it (83% of the frame at jump zoom 1.1, 69% at punch 1.2, about 32% when a landscape source is cropped to 9:16).
ChangeFor jump, punch and no-zoom segments, put the crop ahead of the conversion so only the kept window is converted. The slow-zoom path scales before it crops, so it is left as is.
Why class BCropping is pure selection and the conversion is per pixel, so the interior is the same. The conversion upsamples the chroma planes using neighbouring pixels; at the crop border it now sees clamped edges instead of the real neighbours, so the outermost row and column can differ by a rounding step. Nothing visible. Item 1 is the bigger HDR saving; this one stacks on top of it.

12. Crop first, then scale, for static vlog shots

Where: engine/commands/vlog.py video_chain() line 315: scale (cover), crop.

NowStatic shots scale the whole frame to cover 1080x1920 times the zoom, then crop the centre. render.py's still path already does it the other way round (crop the window, scale once).
ChangeSame trick as render.py: compute the window, crop it from the source, scale once.
Why class BSame sub-pixel class as the change already accepted in render.py: the scaler's sampling phase can shift by a fraction of a source pixel. The gain is small for portrait 9:16 sources at zoom 1.0 (no crop needed) and only matters for the tighter 1.15 framings and landscape clips, so this is low priority.

C. Look into before touching

13. Map the hidden pixel-format conversions

Where: the whole video chain in engine/commands/render.py build(); grade_filter() in engine/core/grade.py line 28.

FactsThe DJI source is 10-bit (yuv420p10le); the hardware decoder returns 10-bit frames. Crop and scale keep whatever they are given. The 22 segments meet at concat, which needs one common format. The colour table filter (lut3d) only accepts RGB formats, so the whole graded timeline is converted to RGB and back. The sharpen filter accepts planar YUV and planar RGB. The b-roll overlay defaults to processing in 8-bit 4:2:0 and converts both of its inputs to that. The encoder wants 8-bit 4:2:0. ffmpeg fills every gap with an automatic conversion filter, and none of those are visible in filter.txt.
SuggestionRun one render with -loglevel verbose and list the lines mentioning auto_scale. Then, and only then, make a conversion explicit where it is provably redundant (two conversions back to back, or a conversion that a neighbouring filter would do anyway). Do not force 8-bit before the colour table: on a 10-bit source the grade is currently applied at higher precision, and dropping to 8-bit first would change the look.
ObservationOutside the brief, but worth knowing. The colour table and the sharpen filter share only one format family, planar RGB, so that is likely what ffmpeg negotiates between them. The sharpen filter treats plane 0 as "luma" and planes 1 and 2 as "chroma" (chroma amount is 0, so untouched). In planar RGB, plane 0 is green. If that negotiation is what happens, the clarity step currently sharpens only the green channel. The amount is tiny (0.1), so the visible effect is minimal either way, but it is a look matter to check, not a speed one.

14. The zoom filter is the hot spot

Where: zoompan in engine/commands/render.py lines 151 and 460, engine/commands/vlog.py line 312, engine/commands/textreel.py line 223.

Why slowIt runs on one core (no slice threading), it rebuilds its scaler for every output frame because the crop size changes each frame, and it works from the 2160x3840 canvas (8.3 million pixels in, 2 million out, bicubic). Every slow-zoom segment, every b-roll shot and every text-reel shot goes through it. The 2x canvas is deliberate (half-pixel steps keep the push smooth), so the input size cannot shrink without changing the motion.
Possible stand-inThe same maths, an integer crop followed by a bicubic scale, can be written as crop with time expressions plus scale, and the scale filter is slice-threaded. In theory the same pixels; in practice there are two places it may not be: how the crop position rounds on the chroma planes at odd offsets, and the scaler flags. It needs a frame-by-frame comparison on a real reel before anyone adopts it. Not recommended blind.

D. Previews only

15. Half-size drafts, and fold the flash scan into the preview render

Where: engine/commands/render.py --draft (lines 880 to 889) and _render_windows() lines 738 to 746.

DraftsA draft currently runs the full 1080x1920 chain and only saves on the encoder bitrate, which is the cheap part. Cut previews already render at half size for about 4x less filter work; drafts could use the same path. Finals untouched.
Flash scanEach cut-preview window is encoded, then decoded again by a second ffmpeg for the scene-change scan. A split in the same filter graph could feed the scan branch from the pre-encode frames and write it to -f null. The preview video is unchanged; the detector would see cleaner frames than the decoded preview, so the scan input differs slightly. Threshold 8 is coarse, but it is a different input to a check, so flagging it.

Already good, leave alone

  • Hardware decode on every video input through vin(), with the automatic software retry.
  • The grade baked into one 3D colour table (one pass instead of five), rebuilt only when grade.json changes.
  • Still framings crop the exact window and scale once.
  • Each segment reads only its own stretch of the source (-ss/-t per input), so unused footage is never decoded.
  • The b-roll 2x "scale" is a no-op on the library clips, which are already 2160x3840; the scale filter passes frames through when nothing changes.
  • Scene cuts cached per file identity; music analysis cached per track.
  • Shop intermediates stay HEVC and never get uploaded; finals are hardware h.264 with the quality priority on.
  • Three renders at a time for sets, per the skill (item 5 just moves that rule inside the scripts).

How to check any of these safely

For an A-class change, render the same plan before and after to a lossless intermediate and compare frame hashes; the lists should match line for line:

ffmpeg -i before.mp4 -map 0:v -f framemd5 before.md5
ffmpeg -i after.mp4  -map 0:v -f framemd5 after.md5
diff before.md5 after.md5

That only works when both sides were encoded losslessly (for example -c:v ffv1 on a short test plan), because the hardware encoder is not guaranteed to produce the same bytes twice. For B-class changes, a PSNR comparison is the right tool: anything above about 50 dB is below what the h.264 encode itself does to the picture.

ffmpeg -i before.mp4 -i after.mp4 -lavfi psnr -f null -
